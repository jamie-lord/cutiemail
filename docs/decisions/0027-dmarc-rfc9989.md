# 0027. Which half of RFC 9989 this server implements

## Status

Accepted (2026-07-28).

## Context

RFC 9989 (May 2026) obsoletes RFC 7489. Every line of DMARC in this repository follows RFC 7489.
RFC 9989 is not a clarifying revision. Four things change that a receiver can observe:

1. **Policy discovery.** 7489 §6.6.3 queries `_dmarc.<Author Domain>`. If that query fails, 7489
   goes directly to the Public Suffix List organizational domain. 9989 §4.10 replaces that with a
   DNS tree walk up the name, one label at a time.
2. **The organizational domain itself** is no longer a PSL lookup. It is whichever name in the walk
   published a record, and a new `psd` tag disambiguates it. §4.10.2 requires a separate walk per
   authenticated identifier for alignment checks.
3. **`pct` is gone.** Appendix A.6 and the IANA registry retire it to historic. A `t` test-mode tag
   replaces it. The `t` tag demotes the policy one level. It does not sample a share of failures as
   `pct` did.
4. **`np`** applies a distinct policy to non-existent subdomains.

The PSL jump is not merely dated. It loses policy that domain owners published. Consider an Author
Domain `alerts.corp.example.com`, where `corp.example.com` publishes `p=reject` and the apex
publishes nothing. 7489 discovery looks at the Author Domain, then `example.com`. It finds neither
and applies no policy at all. The record exists in DNS and says reject, and this server still
delivered the message to the inbox.

That same gap runs the other way and reaches our own operators. The deployment guide recommends a
mail domain below the registered domain (`you@mail.example.com`). Under 7489, the `_dmarc` record
that `setup` generates for it governs exactly that one name. A receiver that evaluates
`billing@anything.mail.example.com` skips it and consults `_dmarc.example.com` instead. 9989's walk
visits the intermediate name and finds ours. The receivers that decide today are still the ones that
matter, so `doctor` gained a `dmarc-org` check for the apex record as well. The two fixes address the
same hole from opposite ends, and neither replaces the other.

Full adoption of 9989 is a different size of job. §4.10.2 alignment means up to eight queries for
the Author Domain plus eight for each DKIM `d=` and the SPF domain, on an unauthenticated path, per
message. `np` needs a non-existent-domain determination this server does not make. `psd` needs the
walk to continue past the registered domain to the TLD. None of that is hard in isolation. Together
it is a rewrite of the DNS layer of DMARC, and it buys least where this server runs.

## Decision

**Adopt policy discovery and test mode. Keep the Public Suffix List for alignment. Implement neither
`psd` nor `np`.**

**Discovery walks the ancestors, floored at the PSL organizational domain** (`policyAncestors` in
`server/dmarc-inbound.ts`). A record at the Author Domain still wins outright and still costs one
query. Otherwise the walk queries the organizational domain first and works downward. It takes the
first hit.

Downward is not an optimisation. It is the specification. §4.10.2 selects "the DMARC Policy Record
found at the name with the fewest number of labels". So where both an intermediate name and the apex
publish, the *shallowest* record governs. That is the opposite of the intuition that the most
specific one should govern. A downward walk that stops at the first hit computes that selection
directly. It means the ordinary two-label sender costs the same two lookups it always did.

The floor is what buys the simplicity. A walk that never goes above the registered domain has no
`psd` tag to interpret, and no way to apply a public suffix operator's policy to a domain that never
asked for one. Its bound falls out of the PSL rather than from a rule of its own. §4.10's own cap
still applies on top. An Author Domain of eight or more labels reduces to its seven-label suffix. So
a From header of two hundred labels cannot buy two hundred DNS queries from an unauthenticated peer.

The change is close to monotone. Every message that gets a policy under 7489 gets the same policy
here, because the walk queries the organizational domain first, and that domain wins when it
publishes. What changes is a record published *between* the Author Domain and the organizational
domain. The server now applies it where it previously ignored it. This holds in either direction,
since the intermediate name may as easily publish `p=none` as `p=reject`. That is the domain owner's
stated preference either way.

**`t=y` demotes the governing policy one level** (§4.7): reject becomes quarantine, quarantine
becomes none. `checkDmarc` returns the *demoted* policy as `policy` and the undemoted one separately
as `publishedPolicy`. The `publishedPolicy` value is for the `Authentication-Results` trace and
nothing else. There is deliberately no field the enforcement path could pick wrongly. The one value
it reads is already correct, and test-mode support required no change at the enforcement site at all.

Only a literal `y` demotes. §4.7 makes `n` the default. So a garbled value fails toward the published
policy: the server enforces it rather than a silent disarm.

**`pct` stays.** It is historic in 9989, and senders who wrote their records against 7489 still
publish it in quantity. To drop it would enforce in full against domains that asked for a sample.
That is the same over-enforcement that a disregard of `t` would cause, just aimed at the other era's
senders. Support for both costs one boolean and one comparison.

**The parser does not add `np` and `psd` to its known-tag set.** They are real 9989 tags. To list a
tag whose semantics the server ignores would claim otherwise. To leave them unknown-and-ignored is
both honest and what §6.3 requires. A published `np` has no effect, and the `sp`/`p` default governs
instead.

## Consequences

- The server now enforces a DMARC policy published at an intermediate name. On a personal deployment
  the most likely place to notice is mail from large organisations with per-department subdomains.
- Discovery can cost up to eight DNS queries where it previously cost two, but only for an Author
  Domain several labels below its registered domain. The common cases — a record at the Author
  Domain, or one label below it — are unchanged at one and two queries.
- A domain part-way through a DMARC rollout, which publishes its target policy with `t=y`, now
  reaches the inbox instead of Junk. An operator is most likely to mistake this change for a
  regression. So the trace reads `dmarc=fail (p=quarantine t=y)` rather than a bare `p=none` that
  would look as though the zone said nothing.
- Alignment still compares PSL organizational domains. Where 9989's per-identifier tree walk would
  disagree — a sender that publishes records at intermediate names specifically to *split* alignment
  between departments — this server aligns them where 9989 would not. That is a real divergence, and
  nothing above fixes it. **Revisit** if you ever observe a legitimate sender that relies on it, or
  if the PSL's refresh cadence becomes the thing that breaks alignment.
- Multiple published records at any one name still terminate discovery with no policy applied, per
  7489 §6.6.3 step 5. 9989's walk continues past them. This can only matter once the organizational
  domain publishes nothing, so it cannot lose a policy that 7489 would apply. It is a deviation all
  the same, and `doctor` now reports the case for our own zone.
- The repository vendors `spec/rfc9989.txt` alongside `spec/rfc7489.txt`. Both stay. The alignment
  and grammar requirements still cite 7489, the specification the deployed senders followed.

## Consequences for the register

Six requirements added, all cited to `rfc9989`: `R-9989-4.10-a` (the eight-query bound),
`R-9989-4.10.1-a` (walk when the Author Domain has no record), `R-9989-4.10.1-b` (`sp` governs a
record found above the Author Domain), `R-9989-4.10.2-a` (fewest labels wins), `R-9989-4.7-a`
(test mode) and `R-9989-11.5-a` (evaluate every author domain, strictest failing policy wins). The
7489 grammar and alignment entries are unchanged.

A later audit added the last of those rather than the rest, and the gap it closed is worth naming.
This server already treated more than one author mailbox as never-authentic, and already forced such
a message to `fail`. It did not pick the policy on any principle the attacker could not override. It
evaluated a single mailbox, and the extractor takes the LAST one. So an attacker who appended a
policy-less domain of their own left the victim's address displayed first and the failure unenforced.
Detection of a spoof, and then no action on it, is worse than either alone, because the trace says
`dmarc=fail` while the message sits in the inbox. §11.5 also warns that evaluation of every domain is
itself a denial-of-service vector. So the server caps both the domain count and the total lookups per
message.

`RequirementDef.page` became optional. The RFC Editor's current text format has no page breaks —
RFC 9989 carries zero `[Page N]` markers where RFC 7489 carries 73 — so for those documents the
section number is the only locator. A page number would be a figure no reader could check against the
vendored file.
